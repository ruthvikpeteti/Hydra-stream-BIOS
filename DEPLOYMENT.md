# SovereignStream — Phase 1 Deployment (Kafka regional infrastructure)

Docker Compose implementation of the three independent regional clusters from [ARCHITECTURE.md](ARCHITECTURE.md) §5–6. This phase contains only the Kafka data plane and basic monitoring. No gateway, replicator or control plane exists yet.

Requirements: Docker with Compose v2, about 4 GB free memory for the containers, `python3`, `curl`. Tested with Docker 29.9 and Compose 5.6 on macOS, image `apache/kafka:3.9.0`.

## 1. Layout

```
infrastructure/
  docker-compose.yml        all services, networks, volumes
  .env                      generated cluster IDs (git-ignored)
  kafka/                    per-region broker settings (region-a.common.env, region-b.env, region-c.env)
  config/                   client configs (producer/consumer), Prometheus config, env.example
  scripts/                  start/stop, init, topic, produce/consume helpers
  tests/                    Tests A–E and run_all.sh
```

## 2. Topology (local development profile)

| Region | Containers | Metadata quorum | Cluster ID | Local durability | Host ports |
|---|---|---|---|---|---|
| A | `ss-a-controller-1..3` (dedicated), `ss-a-broker-1..3` | 3 controllers, ids 1–3 | `CLUSTER_ID_A` | RF 3, `min.insync.replicas=2` | none by default (debug override: 29092–29094) |
| B | `ss-b-kafka-1` (broker+controller combined) | 1 node, id 201 | `CLUSTER_ID_B` | RF 1, min ISR 1 | none by default (debug override: 39092) |
| C | `ss-c-kafka-1` (broker+controller combined) | 1 node, id 301 | `CLUSTER_ID_C` | RF 1, min ISR 1 | none by default (debug override: 49092) |

Monitoring: `ss-a-exporter` :9308, `ss-b-exporter` :9309, `ss-c-exporter` :9310 (Prometheus metrics, for example `kafka_brokers`, `kafka_topic_partition_in_sync_replica`). Optional Prometheus on :9090 (`--monitoring`).

Region A uses dedicated controllers, not combined roles. With three combined nodes, stopping two brokers would also break the metadata quorum, and the "one ISR left" case could not be tested cleanly. If memory is tight you can switch A to combined roles by giving each broker `KAFKA_PROCESS_ROLES=broker,controller` and removing the controller services. Test D would then see produce timeouts instead of `NotEnoughReplicasException`.

### Isolation and listeners

- **Separate clusters:** each region has its own cluster ID (generated by `init-cluster-ids.sh`, checked to be distinct), its own KRaft voter list, its own volumes and its own network (`ss-region-a-net`, `-b-`, `-c-`). No container is on two region networks, so a region cannot even resolve another region's hostnames (asserted in Test A).
- **No stretched cluster:** nothing in the compose file links regions. Cross-region replication arrives in a later phase through explicitly approved links ([ARCHITECTURE §4.2](ARCHITECTURE.md), INV-2).
- **`ss-monitoring-net`:** metrics only. Exporters sit on their region's network plus this one. It carries no Kafka traffic.
- **Listeners:** `CONTROLLER :9093` (quorum), `INTERNAL :9092` (broker-to-broker and in-region clients, advertised as the container name), `EXTERNAL` (advertised as `localhost:<port>`). **Since Phase 2 no Kafka listener is published to the host or attached to the client network**: producers and consumers must go through the gateway ([GATEWAY.md](GATEWAY.md)). The scripts here use the INTERNAL listener from inside the containers. For debugging only, `scripts/up.sh --expose-kafka` adds `docker-compose.expose-kafka.yml`, which publishes EXTERNAL ports 29092–29094 (A), 39092 (B), 49092 (C) and switches the gateway-only guarantee off (the gateway test for it is then skipped).
- **Client network:** `ss-client-net` carries only the gateway (published on host port 8080). The gateway is also on `ss-region-a-net`. It is on no other region's network.
- **Security:** PLAINTEXT for local development only. TLS/mTLS and ACLs are part of the production design (SECURITY.md) and are not configured here.

## 3. Startup, shutdown, cleanup

```bash
cd infrastructure
scripts/up.sh                  # generate cluster ids + gateway API key if missing, build and start all incl. the gateway, wait healthy (~2 min first time)
scripts/up.sh --monitoring     # also start Prometheus on :9090
scripts/up.sh --expose-kafka   # DEBUG ONLY: publish Kafka listeners to the host (disables the gateway-only model)
scripts/status.sh              # health, cluster id, quorum leader/voters, exporter checks
scripts/init-topics.sh         # optional: ss.smoke topic in each region (A: 3 partitions RF 3; B, C: RF 1)

scripts/down.sh                # stop and remove containers and networks; DATA IS KEPT in volumes
scripts/down.sh --volumes      # ALSO deletes all Kafka data in all regions (irreversible)
scripts/init-cluster-ids.sh --force   # new ids; only after --volumes (old data is bound to the old id)
```

Single container control for experiments: `docker stop ss-a-broker-2`, `docker start ss-a-broker-2`. Volumes are named `ss-<node>-data` (`docker volume ls | grep ss-`). Deleting only `.env` while volumes exist makes brokers fail at startup with a cluster-id mismatch. That is intended.

Container and volume names are fixed (`container_name`, `name:`) so scripts and tests can address them directly.

## 4. Test and demo scripts

| Script | Use |
|---|---|
| `scripts/create-topic.sh <a\|b\|c> <topic> [partitions] [rf]` | Create a topic with the region's `min.insync.replicas`. |
| `scripts/produce-events.sh <region> <topic> [count] [keys]` | Keyed events `key-k:seq`, `acks=all` from `config/producer.properties`. `SEQ_START`, `PRODUCER_EXTRA` env overrides. |
| `scripts/consume-events.sh <region> <topic> [max] [timeout-ms]` | Prints `partition key value`; uses no consumer-group commit. |
| `scripts/describe-topic.sh <region> <topic>` | Partition, leader, ISR. |

Example: `scripts/create-topic.sh b demo 3 && scripts/produce-events.sh b demo 20 && scripts/consume-events.sh b demo 20`.

## 5. Automated tests

With the stack up: `tests/run_all.sh` (about 1 minute). Tests C–E are stateful and must run in order. They keep state in `tests/.state/` and leave region A fully restored when E passes.

| Test | Verifies |
|---|---|
| A | All containers healthy; each cluster's own reported ID equals the configured one and the three differ; A has 3 voters and 3 brokers, B and C have 1 each; Kafka host ports are closed (or, with `--expose-kafka`, every external listener answers a Kafka ApiVersions request); regions cannot resolve each other; exporters respond. |
| B | Topic in A with 3 partitions, RF 3, min ISR 2; 1000 keyed events with `acks=all`; consumption returns exactly 1000 events, no duplicates, per-key order preserved (Kafka orders per partition, so ordering is checked per key). |
| C | Stops the leader of partition 0; every partition gets a new leader that was in the previous ISR (unclean election is disabled); the stopped broker leaves the ISR; 200 more `acks=all` writes succeed with ISR=2; all 500 events consumed. |
| D | Stops a second broker; waits for ISR=1; an `acks=all` produce with no retries fails with `NotEnoughReplicasException`. |
| E | Restarts both brokers; ISR returns to 3 for all partitions; writes resume; 600 events present exactly once (the rejected writes from D are absent). |

Last recorded run (this machine): A–E all passed. Also verified: after `down.sh` without `--volumes` and a fresh `up.sh`, all 600 events were still consumable.

Test limits worth knowing: C and D use graceful `docker stop`, which makes brokers leave the ISR immediately. A hard kill (`docker kill`) instead relies on `replica.lag.time.max.ms` (set to 10 s in `kafka/region-a.common.env` to keep tests fast; the Kafka default is 30 s). Test D proves rejection for new writes. It does not prove behaviour of producers that use `acks=1`, which bypass min ISR by design, and which SovereignStream's gateway will never use.

## 6. Configuration reference (region A)

`default.replication.factor=3`, `min.insync.replicas=2`, `unclean.leader.election.enable=false`, `auto.create.topics.enable=false` (topics are created explicitly so that policy, not defaults, sets durability), `offsets.topic.replication.factor=3`, `transaction.state.log.replication.factor=3`, `transaction.state.log.min.isr=2`. Producer `acks=all` plus idempotence is the client default in `config/producer.properties`. Consequence: with two brokers down, consumer-group coordination (which writes to `__consumer_offsets`) also stops in A, as it should.

## 7. Production design (not what this Compose file provides)

Per region: at least 3 brokers across 3 failure domains (rack/AZ-aware placement), RF 3, `min.insync.replicas=2`, plus a dedicated KRaft controller quorum of 3 nodes (5 for stricter needs) separate from the brokers. Each region has its own quorum and cluster ID. No quorum spans regions. TLS everywhere, ACLs per principal, and per-region secrets and KMS, per [SECURITY.md](SECURITY.md).

The MVP profile for B and C (one combined broker+controller node, RF 1) is a demonstration profile. It has no broker or controller fault tolerance, and a restart makes the region unavailable. It must not be presented as production HA. Production regions B and C must match region A's design. See [ARCHITECTURE §6](ARCHITECTURE.md).

## 8. Known limitations in Phase 1

- The Kafka exporter image has no shell, so those three containers have no Docker health check. Check `/metrics` (done by `status.sh` and Test A).
- Heap sizes are small (192 MB controllers, 384 MB brokers) for laptops. Not a performance configuration.
- No cross-region replication, topic policy enforcement or gateway yet.

## 9. Phase 2: gateway service

`ss-a-gateway` (built from `gateway/`, image `sovereignstream/gateway:phase2`) serves the HTTP API on `http://localhost:8080/api/v1`. The client API key is `SS_GATEWAY_API_KEY` in `infrastructure/.env` (generated by `scripts/init-cluster-ids.sh`, sent as `X-API-Key`). The gateway is stateless (topic policies and idempotency records live in Kafka), so it has no volume of its own. Its dev control-plane stand-in is `infrastructure/config/control/dev-control-state.json`, mounted read-only. Tests: `gateway/tests/run.sh` (about 80 s; needs the stack up). Details, API and limits: [GATEWAY.md](GATEWAY.md).

## 10. Phase 3: policy engine, PostgreSQL and regional agents

| Service | Purpose | Host port | Networks |
|---|---|---|---|
| `ss-postgres` (volume `ss-postgres-data`) | Policy, registry, assignments, audit log | none | `ss-control-net` |
| `ss-policy-engine` | Engine API | 8090 | `ss-control-net` |
| `ss-a-agent`, `ss-b-agent`, `ss-c-agent` | Regional agents (each also on its own region network, to reach its cluster) | 8091, 8092, 8093 | `ss-control-net` + region net |

`ss-control-net` carries policy traffic only; no Kafka broker is on it. The gateway joins it to reach the engine. `scripts/init-cluster-ids.sh` also generates the PostgreSQL password, three engine API keys (admin, writer, service) and an Ed25519 bundle-signing key pair in `infrastructure/config/keys/` (git-ignored); every secret is masked in the script's output. The engine seeds regions A (EU), B (EU) and C (US) from `policy/config/seed-registry.json` on first start. Agent and engine host ports exist for operators and tests; keep them internal in production.

`scripts/up.sh` now always rebuilds images. Tests: `policy/tests/run.sh` (pure and property tests need nothing running; integration tests need the stack and take about 90 s, including a 36 s stale-policy wait). Details: [POLICY.md](POLICY.md).

## 11. Phase 4: replication agents and receivers

| Service | Purpose | Host port | Networks |
|---|---|---|---|
| `ss-{a,b,c}-replicator` | Source agent: replicates its region's topics to authorized targets; `GET /status`, `/health` | 8095, 8096, 8097 | `ss-control-net` + region net |
| `ss-{a,b,c}-agent` | Also hosts the receiver `POST /internal/v1/replication/batches` | 8091-8093 | as before |

`scripts/init-cluster-ids.sh` also generates `SS_REPL_KEY_A/B/C` (one secret per source region; a receiver accepts only the key belonging to the region the batch claims to come from). `SS_FAULT_INJECTION=1` (default in the dev compose) enables the test-only fault endpoint on receivers; set `0` anywhere that is not a test stack. The image is `sovereignstream/policy:phase4`. Start replication for a topic with `POST /api/v1/replication/topics/{topic}/start` (writer key). Details and limits: [REPLICATION.md](REPLICATION.md). `tests/run_all.sh` now also runs `test_f_replication_e2e.sh` (about 3 minutes).

## 12. Adaptive routing and fault injection (Phase 5)

`ss-toxiproxy` fronts every inter-region path (config `infrastructure/chaos/toxiproxy.json`, generated by `chaos/gen_paths.py`). Use the scripts in `infrastructure/chaos/` to inject latency, jitter, bandwidth limits, resets, disconnects and recovery. See [ROUTING.md](ROUTING.md) for behaviour, tuning and limits.

## 13. Disaster recovery stack (Phase 6)

```
infrastructure/scripts/up.sh --dr          # adds: 5-member etcd (a, b, c + witnesses w1, w2), gateways in B and C, two DR controllers
infrastructure/scripts/dc.sh <compose args> # docker compose with the DR overlay (e.g. dc.sh logs ss-dr-1)
policy/tests/dr_run.sh                     # the DR scenarios, each on a fresh stack. DESTRUCTIVE (deletes all data of the project)
```

In `--dr` mode the gateway in A (and B, C) takes its lease from etcd instead of the Phase 2 dev control file, so the Phase 2 gateway tests that edit that file are not meaningful in this mode (run them without `--dr`). `SS_DR_ALLOW_DEGRADED_RPO=1` lets an operator approve a promotion outside the RPO; it is off by default. Controller API: `GET /dr/v1/status` (ports 8101, 8102), admin-key POST `/dr/v1/failover`, `/dr/v1/failback/{start,approve,abort}`. Fault-injection endpoints (`/dr/v1/debug/*`) exist only while `SS_DR_FAULTS=1` (default on in this dev stack: set 0 elsewhere). See [DR.md](DR.md).

## 14. Dashboard (Phase 7)

`scripts/up.sh --dr` also starts `ss-dashboard` (http://localhost:8200; built from `dashboard/Dockerfile`, build context = repository root). Tokens: `SS_DASH_VIEWER_TOKEN` / `SS_DASH_OPERATOR_TOKEN` in `infrastructure/.env` (generated by `init-cluster-ids.sh`, masked in its output). Prometheus (`--monitoring`) scrapes `ss-dashboard:8200/metrics`. Development UI: `cd dashboard && npm install && SS_DASH_API=http://localhost:8200 npm run dev`. Tests: `dashboard/run_tests.sh unit|live|e2e-destructive`. Details, permissions, metric label policy and limits: [DASHBOARD.md](DASHBOARD.md).
